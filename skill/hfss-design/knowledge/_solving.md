# 求解与工程运维经验(不限天线类型)

`_general.md` 管**建模**、`_optimization.md` 管**扫参/匹配**,本篇管**跑求解本身**:
setup/扫频怎么组织、结果可不可信、求解崩了怎么判、会话挂了怎么恢复。
开工前若要跑长求解、或求解莫名变慢/失败/结果可疑,先读这篇。

---

## setup 分工:调参期间工程里只留一个 setup、一条不存场的插值扫频

- **调参 setup**:一个,挂**一条**插值扫频,`save_fields=False`。
- **远场 setup**:另建,只挂存场扫频(`sweep_type='Discrete', save_fields=True`),
  **只建真正要看的频点**,尺寸定稿后跑一次。
- 机理:`analyze(setup)` 会把**这个 setup 下所有启用的扫频**一起解;调参每轮都改变量,
  新变量组合没有解,这些扫频每轮都得重算。存场频点每个都要单独解一遍并落一份完整场,最贵。
  别的 setup 不会被 `analyze(setup)` 解到(2019.2 对照实测),但 GUI 的 Analyze All 会。
- 用完的扫频 `delete_sweep` 掉(要留的曲线先取数)。删扫频会连带删掉它的结果。

**诊断手法(求解器到底在算什么)**:结果目录 `<工程>.aedtresults/<design>.results/` 里文件名形如
`DV<变量组合>_S<id>_*`,按修改时间排序就知道这段时间在写哪个 setup/扫频:
自适应各轮是 `_SD<n>_*.su`,插值扫频每个基点是 `_F<n>_SU.txt`,存场离散点是**目录**(内含 `.nvc/.tvc`)。

## 扫频类型选择:别默认"Fast 一定更快"

Fast(ALPS)要对整个大矩阵分解再建降阶模型,网格越大这步越贵,内存一紧张优势就没了,
可能比插值扫频还慢。要比,就在已收敛的同一几何上**加一条** Fast 扫频再 analyze
(复用网格、只解新扫频),和插值逐点对比,比完删掉不用的那条。

- **扫频范围要留出谐振移动的余量**。调参时谐振会跑,范围卡太紧它会跌出边界,
  读数上像"谐振消失"——**先怀疑扫频范围,再怀疑物理**。
- **尖锐极点会让插值扫频疯狂补点**(如带内集总 LC 陷波器),耗时翻几倍。
  判据:按时间顺序看各基点频率,后段高度聚集就是在追某个尖特征。

## 结果可不可信

### 欠收敛的自适应会"吃掉"谐振
同一几何扫长度,谐振位置高度非单调、中间几个取值**谐振整个消失**,多半是那几组自适应没收敛
(卡在 `max_passes` 上限)——欠收敛的解会丢掉较弱的谐振。
- 单个变量组合看 `analyze` / `get_convergence` 返回的 `converged`。
- **参扫要逐组核对**:`get_parametric_results` 不会告诉你哪组欠收敛。各组的收敛数据在
  结果目录的 `*EMConvData` 里(`PassNo` / `SolvedElements` / `MaxMagDeltaS`),
  或在 `get_messages` 里找 `Adaptive Passes did not converge`。
- 收不到就给足 `max_passes`;仍收不到改用局部网格加密(压在细缝/强耦合区),而不是一味加轮数。

### 只改边界/材料不动几何:HFSS 接着旧网格往下跑
补了 PE、改了材料后重解,HFSS **不重剖网格**,而是沿用上次的自适应网格、**接着上次的遍数继续**
(2019.2 对照实测:补 PE 后收敛表前 5 遍单元数与补之前逐个相同,只新跑了 1 遍)。
网格是按改之前的边界细化的,而且上次已经用到 `max_passes` 上限时,这次只剩一两遍可跑。
⇒ 修了边界/材料,看收敛表的单元数和遍数;要强制从头自适应,`delete_setup` 后重建 setup
(重建的 setup 从初始网格开始,不复用旧解)。改几何变量则本来就会从初始网格重剖。

### 镜像等价:一条免费且精确的收敛性自检
任何结构的**镜像体**与原体有严格恒等的 S 矩阵(端口按镜像置换重新编号);
**位于镜像面上的端口,其 `S(Pk,Pk)` 必须逐点相同**。这是物理恒等式,不依赖参考解
⇒ 两边对不上,至少有一边没收敛到位——哪怕 HFSS 两边都报"收敛"。
N 重旋转对称结构同理:各口 `S(Pk,Pk)` 的散布就是收敛误差的直接读数。

### 多频/双频:单频自适应管不住远处的窄带模
单频自适应只保证**该频点**的 S 收敛。离它远的窄带高 Q 模(寄生枝节、耦合缝支撑的第二频段)
在该频点场很弱,ΔS 看不见它 → 谐振位置随网格漂移,HFSS 照报"收敛"。
⇒ 两个频段的天线用 `create_setup(frequencies=[f1, f2])` 在两个带中心同时自适应,别取中间频率。
多频点自适应网格涨得更快,注意内存。

### 别拿 S 曲线的"最小值"比对互耦
`min_value_dB` 是整条曲线的最小值:对 Sii 是谐振深度,有意义;对 Sij 是"耦合最弱的那个零点",
超敏感,拿它比两个模型会得出完全错误的结论。⇒ 比互耦用 `summary_only=false` 在关心的频点上逐点比。

### 取远场前先确认 setup 的自适应频率落在谐振上
`get_radiation_pattern` 默认取 `LastAdaptive`,即 setup 自适应频率那一点。几何/材料改了谐振会移,
自适应频率可能落到谐振之外(双频天线两带之间就是失配峰),realized gain 含失配损耗,看着像天线被改坏了。
⇒ 对一下 `get_s_parameters` 的 -10dB 区间,setup 频率不在里面,远场就不能用;
为要考察的谐振点单建 setup(频率设在谐振上),需要的话顺手挂一条存场离散扫频。

## 网格与内存

- **长度型网格算子跟着对象走**:对象被加长、unite 进更大的对象后,原来的 `assign_mesh_length`
  照样作用在整个新对象上,初始网格可能暴涨直至 OOM。改几何前先看哪些网格算子挂在被改的对象上;
  求解前看 profile 的 Manual Refine 行(列出生效的算子和四面体数)。
- **OOM 可能在跑了很久之后才发生**(自适应后几轮网格最大),"还在跑"不等于"能跑完"。
  长求解先用较少 `max_passes` 试跑估网格规模;提高自适应频率、改多频点自适应都会显著推高网格量。
- 看内存**盯 hf3d 的 PrivateMemorySize,不是 WorkingSet**(换页时 WorkingSet 很小,看着安全)。
  超物理内存就 `Stop-Process hf3d`(AEDT 本体不死),analyze 随后返回 com_error。

## 求解失败与卡住

### 求解崩了不会立刻报错
求解子进程死掉后,COM 调用可能挂很久才返回 `com_error (-2147024349)`(求解器死掉的典型签名)。
- 判断还活着没:(1) `hf3d` 还在不在、内存/CPU 是否在动;(2) 结果目录最近写入时间戳。两者都停 = 已结束或已死。
- 消息窗口写的是 `Simulation was aborted by user`,是有人在 GUI 上按了停止,不是崩溃,别当故障重发。
- 求解期间别从 GUI 或别的脚本对同一实例发建模操作(MCP 这边的调用本来就排队等求解完)。

### 工具调用超时 ≠ 求解失败
超时的只是这次调用,HFSS 会继续解、结果照常落盘。**不要重发 analyze**——会和仍在跑的求解撞车。
按上面的办法看进程和时间戳,等它跑完再用取数工具读结果。

### 求解器子进程起不来(hf3d / MPI)
- 签名:analyze 跑很久后返回 com_error;消息窗口里是 `Unable to create child process: hf3d`、
  `The attempted launch of solvers via MPI failed ...`、`The HFSS solver failed to start`,
  常伴随 `Interpolating frequency sweep did NOT converge`(插值扫频要反复拉起求解进程)。
  这是**求解进程启动失败**,不是模型错误,别急着改模型。
- 报错不一定让结果失效:先看数据是否完整平滑,再决定要不要重跑。
- 另一个表现:求解比预期慢很多倍,profile 里各轮 Elapsed 之和远小于 Adaptive Meshing 总时长
  ——差出来的时间卡在拉子进程上(每次启动失败要等超时)。
- **根治**:HPC 配置的 `UseAutoSettings=true` 会把多频点自适应/插值扫频拆给多个进程并行、走 MPI,
  本机 MPI 起不来就卡。改成**手动、1 个任务(NumEngines=1)、核数不变**,不再走 MPI。
  配置在 `Documents/Ansoft/ElectronicsDesktop<ver>/config/<host>_user.XML` 的
  `DSOConfigurationsEx/HFSS/<当前配置名>` 里(当前配置名看 `ActiveDSOConfigurations`)。
  **必须先关掉 AEDT 再改**(它退出时会回写这个文件),改前备份。这是改用户本机的全局设置,先征得同意。

## 会话/进程挂掉后的恢复

重启 MCP server 会带走它启动的 AEDT 实例;MCP 连着时用户在 GUI 上也关不掉 HFSS 窗口(COM 引用占着)。
**能 `close_desktop` 就别强杀**——强杀是 COM 完全无响应时的最后手段。必须强杀时按序:
1. 确认最后改动已存盘(看 `.aedt` 时间戳)
2. `Stop-Process -Force` 结束 `ansysedt` / 求解子进程
3. 删残留 `<工程>.aedt.lock`
4. **把 `<工程>.aedt.auto` 改名移开**(别删)——否则打开时可能弹"是否从自动保存恢复"对话框,**阻塞 COM**
5. `open_desktop` + `open_project`

- 消息窗口随进程走、不持久化:重开后 `get_messages` 是空的,想查上一轮的告警要在同一个会话里调。
- 强杀后若出现"能打开工程、能列 design,但 `activate_design` / `new_design` 全报 com_error",
  怀疑是许可证 seat 没归还(未验证):重启 Ansys License Manager 服务,或等一阵超时回收。

## 删 setup 再同名重建,原来的参扫接不上
参扫按内部 ID 引用 setup,不按名字。`delete_setup` 后同名重建,原参扫再跑**不会解任何东西**
(2019.2 实测:返回成功、耗时 0.1 秒,没有求解)。⇒ 重建 setup 后必须**新建参扫**指向它。
