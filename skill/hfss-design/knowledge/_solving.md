# 求解与工程运维经验(不限天线类型)

`_general.md` 管**建模**、`_optimization.md` 管**扫参/匹配**,本篇管**跑求解本身**:
setup/扫频怎么组织、求解崩了怎么判、AEDT 会话与 MCP server 挂掉怎么恢复。
开工前若要跑长求解、或求解莫名变慢/失败,先读这篇。

---

## setup 分工:调参期间工程里只留一个 setup、一条不存场的插值扫频

这是本篇最贵的一条经验,**违反它的代价是每轮白等几十分钟到几小时**。

- **调参 setup**:一个,挂**一条**插值扫频,`save_fields=False`。自适应轮数按需要给。
- **远场 setup**:另建,只挂存场扫频(`sweep_type='Discrete', save_fields=True`),**只在尺寸定稿后跑一次**。
- **其余 setup 的扫频全部 `delete_sweep` 删掉**(要留的曲线先取数/导 CSV)。

为什么必须真的删掉:
- **每条扫频都会在之后每一次 analyze 里重算**。实测某工程在远场 setup 上堆到 13 个存场频点后,
  单轮求解从 ~17min 涨到 **62–105min**,结果目录涨到 8.41GB(存场频点约 **90–100 秒/点**)。
- 更隐蔽的一种:**明明只 `analyze(setup="A")`,别的 setup 也会被解**。实测只跑一个粗网格 setup
  (自身开销约 30min),实际耗时 **3 小时**——按时间戳还原,其中近 3 小时在算另一个细网格 setup 的
  251 点插值扫频。已排除 Optimetrics(工程里该段为空)和自适应变慢(各轮自适应都是 5–6min、网格一致)。
  **所以"换个便宜 setup 来调参"这个动作本身不省时间,必须同时把旧扫频清掉。**

**诊断手法(求解器到底在算什么)**:结果目录里每个文件名形如 `DV<变量组合>_S<setupID>_*`。
```bash
find <工程>.aedtresults/<design>.results -maxdepth 1 \
     -newermt "<起始时刻>" ! -newermt "<结束时刻>" -printf "%TH:%TM %f\n" | sort
```
按时间段列出求解器在写哪些文件,`S<setupID>` 直接对上是哪个 setup 在跑。
自适应各轮落成 `_SD<n>_*.su`,插值扫频每个基点落成 `_F<n>_SU.txt`(里面有 `Frequency`、`NumTets`、
`MemoryMasterMB`),存场离散点则落成**目录**(内含 `.nvc/.tvc`)——按这个就能区分扫频类型。

## 扫频类型选择:别默认"Fast 一定更快"

实测同一收敛网格(4 口 QHA、含 0.25mm 细条,网格很细):
插值扫频 **54.0 min** vs Fast(ALPS) **62.6 min**(Fast 慢 16%);精度则极好——101 点逐点最大偏差 **0.048dB**,
极尖谐振(−29.65dB)位置与深度完全一致。Fast 期间求解进程峰值 **10.79GB**、系统仅剩 2.5GB,推断在换页。
- **原因**:Fast 要对整个大矩阵分解再建降阶模型,网格越大这步越贵;内存一紧张优势就没了。
- **验证 Fast 是否划算的正确姿势**:在已收敛的同一几何上**加一条** Fast 扫频再 analyze,
  HFSS 复用网格只跑新扫频,可与插值逐点对比;**比完记得 `delete_sweep` 删掉不用的那条**。

**扫频范围要覆盖谐振可能跑到的地方**。调参时谐振会移动,范围卡太紧会让它跌出下界,
读数上表现为"谐振消失",实际只是没扫到——**看到谐振消失,先怀疑扫频范围,再怀疑物理**。

**尖锐谐振会让插值扫频疯狂补点**。带内若有集总 LC 陷波器之类的尖极点,插值扫频为拟合它会把基点
大量堆在极点附近(实测 37 个基点里 11 个挤在极点两侧 200MHz 内),扫频耗时翻几倍。
判据:按时间顺序把各基点频率打出来,若后段频率高度聚集,就是在追某个尖特征。

## `create_sweep` 不能同名覆盖
同名重建会报 `InsertFrequencySweep 失败: com_error (-2147024381)`。参数建错了要先 `delete_sweep` 再建。
**删扫频会连带丢掉它已求解的结果数据**,删前先把要留的曲线取数存下来。

## 存场:`save_rad_fields` 单独设无效(HFSS 2025.2 实测)
只设"仅存辐射场"时,S 参数照常有解,但**远场报告会报 com_error**。
要在扫频上取远场量(增益/轴比 vs 频率),必须 `sweep_type='Discrete'` + **`save_fields=True`**(存完整场)。
代价是每个频点约 90–100 秒、几百 MB,所以存场频点要精选,且单独放在远场 setup 上。

## 求解崩了不会立刻报错——别靠等工具返回来判断
- 实测求解子进程在 14:48 停止,MCP 调用一直挂到 15:08 才返回 `com_error (-2147024349)`,**空等 27 分钟**。
- **判断是否还活着看两处**:(1) 求解子进程(`hf3d`)还在不在、内存/CPU 是否还在涨;
  (2) `<工程>.aedtresults/<design>.results/` 的最近写入时间戳。两者都停 = 已结束或已死。
- `com_error (-2147024349)` 是"求解器死掉"的典型签名;若消息窗口写的是
  `Simulation was aborted by user`,那是**有人在 GUI 上按了停止**,不是崩溃,别当故障重发。
- **内存是主因**:求解进程解大模型时占 7–11GB;机器内存不够就开始换页,先变慢再崩。

## 长求解期间不要做这两件事
- **不要发任何建模 COM 调用**。HFSS 的 COM 是串行的,求解期间的建模调用不只是排队,
  还可能打断求解器状态——实测求解期间调了一次 `new_design`,55 分钟后 **analyze 直接失败,整轮白跑**。
  求解期间只做不碰 HFSS 的事(本地算坐标、写文档、读论文)。
  (曾怀疑"求解期间并行发只读调用如 bbox 也会打挂 analyze",但那次消息窗口的真实报错是求解子进程
  起不来,**因果未证实**。稳妥做法仍是求解期间不发任何 COM 调用,但别把这当已验证的结论。)
- **不要指望后台 shell 监视叫醒你**。求解进程吃满内存时,轮询式后台监视(PowerShell 轮询、
  `tasklist`、`ls`)会被系统"内存不足"杀掉(实测连续 3 次)。改用磁盘结果目录判断进度。

## MCP 工具调用超时 ≠ 求解失败
工具调用有上限(本环境 2h)。**超时的只是调用,HFSS 会继续解**,结果照常落盘。
超时后**千万不要重发 analyze**——会和仍在跑的求解撞车。正确做法:按上面的诊断手法看进程和时间戳,
等它自己跑完,再用取数工具读结果(解在工程里,不必重跑)。

## 会话/进程挂掉后的完整恢复流程
重启 MCP server **会带走它启动的 AEDT 实例**;重连后 `attach_desktop` 报「操作无法使用」。
**MCP 连着时用户在 GUI 上也关不掉 HFSS 窗口**(COM 引用占着)。按序处置:
1. 确认最后改动已存盘(看 `.aedt` 时间戳)
2. `Stop-Process -Force` 结束 `ansysedt` / 求解子进程
3. 删残留 `<工程>.aedt.lock`
4. **把 `<工程>.aedt.auto` 移开**(改名备份,别删)——否则打开时可能弹"是否从自动保存恢复"的
   GUI 对话框,**阻塞 COM**
5. `open_desktop` + `open_project`
6. **重设端口激励**(多口天线的 ActiveS/极化后处理依赖它,重开后不保留)

其它跨会话失效的东西:
- **`get_messages` 重开工程后返回全空**(消息窗口随进程走,不持久化)——想查上一轮求解的告警
  必须在**同一个 HFSS 会话里**调。
- **参扫解的秒回复用在存盘/重开后失效**(同会话内把 nominal 变量设成某组合值再 analyze 可秒回)。

## 取数前必查:导出文件的时间戳
远场/轴比类工具是"导出 CSV 再解析"的,**设计里缺少必要配置时会静默返回上一次的旧 CSV**。
实测:工程副本里没建无限球,`get_axial_ratio`/`get_radiation_pattern` 直接返回了**前一天**的结果,
数字和旧设计一模一样才被发现。**每次取远场数据先看 `exports/` 里对应文件的时间戳是不是本次生成的。**

## 老版本 AEDT 连不上 COM
旧工程要用老版 AEDT(如 2019)时,`attach_desktop`/`Dispatch` 可能完全连不上。
退路:把工程复制一份,用 `ansysedt.exe -RunScriptAndExit <脚本>` 在副本上跑脚本。
注意老版 `AddMessage` **只吃 ASCII**,脚本里别写中文日志。

## ⚠️ 欠收敛的自适应会"吃掉"谐振——每轮必须核对末轮 ΔS
- **现象**:同一几何扫长度,谐振位置高度非单调,中间几个取值**谐振整个消失**,看起来像物理突变。
- **真相**:那几组自适应**没收敛**。实测同一参扫里,收敛的组末轮 dS **0.0123**,
  "谐振消失"的组末轮 dS **0.030**(都卡在 max_passes=8 的上限)。欠收敛的解会丢掉较弱的那个谐振。
- **判据**:`get_messages` 里的 `Adaptive Passes did not converge based on specified criteria`;
  或直接读磁盘 `<design>.results/*EMConvData`,按 `PassNo` / `SolvedElements` / `MaxMagDeltaS` 看末轮。
  **参扫尤其要逐组核对**——`get_parametric_results` 不会告诉你哪些组欠收敛,照样给你一行漂亮的数。
- **解法**:`max_passes` 给足(宁可 18 也别 8),让它真收到设定的 ΔS;仍收不到就改用局部网格加密
  (`assign_mesh_length` 压在细缝/强耦合区),而不是一味加轮数。
- **推论**:**"粗 setup 和细 setup 对上一次"不等于标定通过**。正确判据是
  (1) 自适应真的收敛到设定 ΔS,(2) 同一几何跑两次结果一致。只凭单次吻合就信任粗 setup,
  后面所有读数里都可能混着欠收敛的假象。

## 删掉 setup 再同名重建,参扫会失效;旧解可能被静默复用
- **参扫按 ID 引用 setup**,不是按名字。`delete_setup` 后同名重建,原参扫再跑直接
  `com_error (-2147024357)`,必须**新建一个参扫**指向新 setup。
- **同名重建后,HFSS 可能复用磁盘上的旧解**:实测把 setup 删掉、以更高 max_passes 同名重建后
  跑单点,耗时只有应有的三分之一,结果与旧解**逐位相同**——等于什么都没验证。
  想强制重解:把某个变量改一个微小量(制造新的变量组合),或换 setup 名。


## 磁盘:用 `cleanup_solutions(scope='fields')` 回收,别删整份解
存场求解很快把结果目录撑到几 GB(实测某工程 8.41GB;单个存场频点几百 MB)。
**场数据是大头,S 参数曲线才几百 KB** —— 所以回收磁盘用 `scope='fields'`:场没了,已画的 S11/带宽/谐振照常能取,不用重跑。`scope='all'` 才是连 S 参数一起删。
⚠️ **删场之后远场量(增益/轴比/方向图)就取不到了**,先把远场取数/导出完毕再清。
不带 `confirm` 调一次会回显结果目录当前占用,可以当"现在占多少盘"的查询用。

## ⚠️ 强杀 HFSS 会泄漏 license seat,攒够了就再也建不了 design
- **现象**:HFSS 能启动、`open_project` 能打开并列出 design,但 **`activate_design` 和 `new_design` 全部报 com_error**
  (`-2147024342` / `-2147024371`),对**所有工程、所有 design** 一视同仁。杀进程、删 `.lock`、重启 HFSS、
  重置 MCP 会话全都无效。
- **原因**:`Stop-Process -Force` 强杀 `ansysedt` **不会归还已签出的 license**,每次留一个悬空 seat。
  一天里为从崩溃中恢复而反复强杀,seat 被占满后就变成上述症状——
  **打开工程只读不要 license,但激活/新建 design 要**,所以表现为"能开能列、不能激活也不能新建"。
- **判据**:`Get-Process lmgrd` 若出现**多个实例**是反复起停的旁证;许可证目录下的日志常常是空的,别指望从那儿看出来。
- **解法**:重启 Ansys 许可证服务(`ANSYS, Inc. License Manager` / License Management Center)释放悬空 seat;
  或等 15–30 分钟超时回收。
- **预防**:**求解卡住优先 `close_desktop`(正常退出会归还 license)**,只有 COM 完全无响应时才强杀,
  并且要意识到每次强杀的代价是漏一个 seat。

## ★ 镜像等价:一条免费且精确的收敛性自检
任何天线的**镜像体**与原体有严格恒等的 S 矩阵(只是端口按镜像置换重新编号);
特别地,**位于镜像面上的端口,其 `S(Pk,Pk)` 必须逐点完全相同**。
这是物理恒等式,不依赖任何参考解 ⇒ **两边对不上,就说明至少有一边没收敛到位**。

实测(L 频段 QHA,把右旋螺旋镜像成左旋):
| | 原体 | 镜像体 |
|---|---|---|
| `dB(S(P1,P1))` 极小值 | **−24.87 @1.528** | **−15.11 @1.532** |
| 求解耗时 | 1438 s | 635 s |

几何逐项核对过是完美镜像(bbox 的 y 严格取反换序,未参与镜像的馈针/端口面/支撑管/地板全部关于镜像面对称),
边界与激励清单也完全一致 ⇒ 差异只能来自数值。而 HFSS **两边都报"收敛"、无任何告警**。

## ⚠️ "新建工程"的网格是从零开始的,不能和累积细化过的老工程比
自适应网格会被后续求解**继承**:同一 design 里改个参数再解,是在上一轮的细网格上继续细化。
所以一个跑了十几轮参数扫描的 design,它的网格远比"同样 setup 配置、但刚建出来"的新工程细
(本例中间好几轮只用 300–400 s 就解完,就是在复用网格)。

⇒ **把设计复制/另存成新工程后重解,结果可能和老工程差很多,而且两边都报收敛。**
- ΔS 是**相邻两轮之间的变化量**,粗网格上也可能偶然变化很小 → 提前满足判据停下;
- 深零点(−25 dB 量级)对网格最敏感,是最先露馅的地方;
- 对策:新工程上**把 ΔS 收紧一档**(0.008 → 0.004)或强制更多轮,再和老工程对齐;
  有镜像/对称关系可用时,优先用上面那条恒等式来判,比互相猜谁准可靠。

## 本机内存上限:约 400–500k 四面体,超了 SOLVER_OUT_OF_MEMORY
实测(16.9 GB 物理内存,HFSS 2025.2 Driven Modal):
- 282k 四面体:正常,23 min
- 406k 四面体:正常,65 min(已接近上限)
- **705k 四面体:第 10 轮自适应时 `Matrix solver exception: SOLVER_OUT_OF_MEMORY`,白跑 69 min**

⇒ **排任务前先估网格规模**,别指望"不行就加密网格"这条退路——它有硬天花板。
把自适应频率往高频挪会显著推高网格量(波长短 + 该处结构细),是最容易撞上限的操作:
同一模型 1.6 GHz 自适应收敛在 406k,改成 1.67 GHz 就冲到 705k 而死。

⚠️ **OOM 是在跑了 69 分钟之后才发生的**,不是一开始就报错 —— 所以"任务还在跑"不等于"任务能跑完"。
长求解要么先用粗档位试跑估网格,要么把 `max_passes` 压到估算的安全轮数。

## ⚠️ 别拿 S 曲线的"最小值"比对互耦
`get_s_parameters` 的 `min_value_dB` 是**整条曲线的最小值**。对 **Sii** 它是谐振深度(有意义);
对 **Sij(i≠j)** 它是"耦合最弱的那个零点",属超敏感量,拿它比两个模型会得出完全错误的结论。

实测教训:比最小值得到"镜像模型互耦掉了 20 dB"(−38.76 vs −17.04),据此判定几何错误;
改按**频点**比对后,1.50–1.52 GHz 两者吻合到 **0.05 dB**,分歧只在窄谐振附近。
⇒ **比互耦一律取 `summary_only=false` 看整条曲线**,并在若干个关心的频点上逐点比。

## ★ 多频/双频天线:单频自适应管不住远处的窄带模 → 用多频点自适应
单频自适应只保证**该频点**的 S 收敛。离它较远的**窄带高 Q 模**(寄生枝节、耦合缝支撑的第二频段)
的场在该频点上很弱,ΔS 看不见它 → 它的谐振位置随网格漂移,而 HFSS 照报"收敛"。

实测(L 频段双频 QHA,自适应 1.6 GHz,ΔS 0.004,带2 是 0.9 mm 耦合缝支撑的窄模):
| 模型(几何等价) | 带2 谐振 | 四口 S(Pk,Pk) 散布 |
|---|---|---|
| 原体 | 1.672 | 0.13 dB |
| 镜像体 A | 1.656 | 0.64 dB |
| 镜像体 B | 1.638 | 1.55 dB |
| 原体 + 曲面逼近 slider 4 | >1.69 | ~2 dB |
四个几何上等价的模型,带2 散了 50 MHz 以上 ⇒ **带2 的所有数字都不能当真**;带1(就在自适应频点附近)只差零点几 dB。

⇒ **两个频段的天线,`create_setup(frequencies=[f1, f2])` 在两个带中心同时自适应**,别取中间频率。
判据仍用对称性:N 重旋转对称结构的 `S(Pk,Pk)` 散布 ≤ 0.2 dB 才算收敛。
⚠️ 多频点自适应网格涨得更快,注意上面的内存上限,先压 `max_passes`。

## ⚠️ 多口顺序馈电(圆极化)的对称自检:必须比**正交**口,且看 S 矩阵的循环类
C4 结构的 S 矩阵是循环阵,按顺序相位馈电时**四个口的 ActiveS 必须逐个相等**。
- ❌ 只比 `S11` 和 `S33`:P1/P3 在同一条轴上,只验了 180° 对称,**查不出 x/y 劈裂**。实测 S11 vs S33 差 0.13dB 的"好解",
  完整看四口时 P1/P3 的 ActiveS −18.6/−19.3dB、P2/P4 却是 **−0.24/−0.81dB**(同一频点)。
- ✅ 比 `ActiveS(P1)` vs `ActiveS(P2)`;定位时按循环类取 S:邻口 S21=S32=S43=S14、对口 S31=S42、对角 S11=S22=…,幅度和**相位**都要对上。
- 机理:圆极化靠一对**简并模**;网格的任何微小不对称都会把它劈开,高 Q 谐振上劈裂量可与带宽相当 → 一组口匹配、正交那组全反射,
  S 矩阵呈 **2 重(x/y)图样**。这是简并劈裂的固有指纹,不代表几何里真有 C2 缺陷。
- 放大效应:ActiveS ≈ 0.08 是若干 0.38 量级耦合项**相消后的残差**,耦合项 7° 的相位误差就能让 ActiveS 摆 5dB。
  ⇒ ΔS 已收敛(0.002)的频段四口 ActiveS 仍可散 5dB;**ΔS 对 ActiveS 精度没有保证**。
- 四口复 ActiveS 取平均 = 对称化矩阵的本征值,可一阶抵消劈裂;劈裂大于带宽时也不准。
- 设计层面的含义:如果连网格级的扰动都能劈开某个谐振,实物公差也会 ⇒ **那个谐振太高 Q,该改设计而不是死磕网格**。

## ⚠️ 长度型网格算子跟着对象走:对象被加长/合并后,算子会把网格撑爆
`assign_mesh_length(objects=[针], max_length=0.25mm)` 原本只作用于 3.2mm 短针;后来把针 unite 成 53mm 长的同轴内导体,
算子照样生效 → **Manual Refine 一步 780k 四面体,第 3 遍 OOM,白跑 46min**。
⇒ 改几何(加长、unite、改尺寸)之前先看 `MeshOperations` 里有哪些算子挂在被改的对象上;**求解前看 profile 的 Manual Refine 行**
(会列出生效的算子名和四面体数),初始网格比上轮大几倍就立刻停。

## ⚠️ 从 .aedt 文本里删了网格算子,HFSS 仍会复用旧的已存网格
删 `.aedt` 里的算子块后重开工程再解,HFSS 直接加载上一轮存下的 `*.cmesh`(profile 里照样列出已删的算子名、同样的 780k)。
⇒ 网格设置变了之后要先 `cleanup_solutions(scope='all')` 清掉旧解和网格再求解。
- **只改边界(补 PE 等)不动几何,同样会复用旧网格**:8×8 阵首轮漏了 63 个贴片的 PE,补上后重解只用 64s,
  profile 里 `Initial Meshing 00:00:00`、只跑了 1 遍 —— 网格是按"只有 1 个贴片是导体"细化的,结果全部失谐(S11 −2~−3dB)。
  ⇒ 修了边界/材料后,**看 profile 的 Initial Meshing 耗时与遍数**,是 0 就说明没重剖;`delete_setup` 重建 setup
  或加/改一个网格算子都能强制从头自适应。

## 多口大阵的内存账:集总口阵列约 45KB/四面体,16GB 机器上限 ~30 万
8×8 微带贴片阵(4λ×4λ、64 个集总口、单频):27 万四面体时 hf3d 私有内存 12.2GB,物理内存剩 0.5GB 开始换页。
同结构 4×4 收敛(ΔS 0.015)用了 21.8 万四面体 ≈ **1.4 万/单元** ⇒ 8×8 收敛要 ~90 万,16GB 机器不可能。
- 开大阵前按"单元数 × 小阵收敛时的四面体/单元 × ~45KB"估内存,超了就换周期单元(无限阵)或缩阵。
- 求解中**盯 hf3d 的 PrivateMemorySize 而不是 WorkingSet**(换页时 WorkingSet 只剩 1–3GB,看着很安全);
  超物理内存立刻 `Stop-Process hf3d`(AEDT 本体不死),MCP 的 analyze 随后返回 com_error(-2147024349)。

## analyze 返回 com_error 时先读消息窗口:可能是求解器子进程起不来(hf3d / MPI)
- 现象:`analyze` 跑了很久后返回 `com_error 发生意外`;消息窗口里是 `Unable to create child process: hf3d`、
  `The attempted launch of solvers via MPI failed while connecting to communication pipes`、`The HFSS solver failed to start`,
  常伴随 `Interpolating frequency sweep did NOT converge`(插值扫频阶段要反复拉起求解进程,最容易撞上)。
- 判据:这是**求解进程启动失败**,不是模型/几何错误,也不一定是并发 COM 调用引起的——别急着改模型。
- 补充(实测):同一 design 里反复出现(11:25、14:42 两次),资源充足(RAM 9GB 空闲、磁盘几十 GB)。
  第二次 analyze 仍返回 ok、151 点数据完整,但耗时从 ~500s 拖到 ~2600s——**报错不一定让结果失效,
  先看数据是否完整平滑,再决定要不要重跑**。
- 补充(2026-10-22 实测,小模型 7 万四面体):**每次启动失败都要先等约 30 分钟超时**。多频点自适应会"Solving Distributed - up to 2 frequencies in parallel",卡在某一轮拉子进程上;profile 里 Adaptive Meshing 总耗时 31 min,而各轮实际求解加起来不到 1 min。一次超时后直接失败,另一次超时后重试成功、结果正常。**判据**:求解比预期慢很多倍时,看 profile 里各轮 Elapsed 之和与 Adaptive Meshing 总时长差多少,差出来的就是卡在启动上。
- ★ **根治(2026-10-22 实测有效)**:卡点在 HPC 配置的 `UseAutoSettings=true` —— 自动模式会把多频点自适应/插值扫频拆给多个求解进程并行,这一步要走 MPI,本机 MPI 起不来就卡 30 分钟。改成**手动、1 个任务(NumEngines=1)、核数不变**,求解不再走 MPI:同一模型从 34–40 min 降到 **3 min**,零报错。配置在 `Documents/Ansoft/ElectronicsDesktop<ver>/config/<host>_user.XML` 的 `DSOConfigurationsEx/HFSS/<当前配置名>` 里(当前配置名看 `ActiveDSOConfigurations`)。**必须先关掉 AEDT 再改**——它退出时会回写这个文件;改前先备份。这是改用户本机的全局设置,先征得同意。
- 排查:先看内存与磁盘余量;工程里开了很多 design、跑过大量求解时资源压力大。偶发的可直接重跑一次;
  反复出现就存盘后重启 AEDT(`open_desktop` 重开),或减少扫频点数/改 Discrete 少点扫频降低进程启动次数。

## ⚠️ `analyze` 返回 ok ≠ 这个 design 真的解好了
- 现象:`analyze` 返回 `{"ok": true, "elapsed_sec": 14.7}`,后续取结果却全是空;
  查 `.aedtresults/<design>.results` 只有 8KB(真解过的同规模工程是 2.8MB)。
- 原因:**求解之后对几何做任何改动,HFSS 会把解整个作废**,而它只在**消息窗口**写一句
  `Solutions have been invalidated. Undo to recover.` —— COM 层面不报错、不返回任何信号。
  "改几何"的范围比直觉宽:**新画一条用来采样的 polyline 也算**。
- **工具已能抓到**:`get_convergence(setup)` 读的是**当前这组设计变量**的收敛表,解被作废后它是空的,
  返回 `has_solution: false` 并直接告警(实测:解完加一根线、不重解直接查,当场报出)。
  `analyze` 的返回值里也带同一检查。
  ⚠️ 别用 `GetValidISolutionList` 判这个 —— 解被作废后它**照样列着**,只能判"从没解过"。
- 解法:看到 `has_solution: false`,或取结果拿不到数,把几何改动做完再 `analyze` 一次。
  要知道是什么改动把解作废的,读 `get_messages`。
- 通用判据:怀疑某个 design 到底解没解,看 `.aedtresults/<design>.results` 的**目录大小**
  —— 几 KB = 没解,几 MB 才是真有解和场。这个判据不依赖任何 API。

## `attach_desktop` 连不上运行中的 AEDT(已在工具里兜住),以及**退出实例会毁别人的工作**
- 现象:`GetActiveObject` 报 `MK_E_UNAVAILABLE`(操作无法使用),但 `ansysedt.exe` 明明在跑。
  实例在跑却不在运行对象表(ROT)里;这时 `Dispatch` 能接上同一个实例。
- 工具已兜底:`attach_desktop` 先试 `GetActiveObject`,失败**自动退回 `Dispatch`**,
  返回里 `connected_via` 写明走了哪条。**退回时不会悄悄新起实例**:之前一个 AEDT 都没在跑就直接报;
  退回后冒出新进程(比如在跑的是别的版本)就判定"不是要接手的实例",关掉它并报错。
  2019.2 不进 ROT,attach 永远接不上它,2019.2 只能 `open_desktop` 新起。
- 接上之后**可以在已开着的工程里干活**(attach 本来就是为了接手它们,`activate_project` 切过去即可);
  护栏只管收尾:不替用户关它们、不退出实例。**不用再改走自己的脚本** —— 走脚本的话,
  `analyze` 返回值里的收敛体检就一条都不起作用(实测吃过这个亏:全程脚本求解,工具层检查全部失效)。
- ⚠️ **更要紧的是另一面:`Dispatch` 在 2025.2 上不是新起实例,是接管已在运行的那个**
  (2019.2 不进 ROT,才每次新起)。那个实例里可能开着用户自己的工程、或别的 Claude 会话的工程。
  实测事故:另一个会话 Dispatch 接管实例、收尾 `QuitApplication`,把开着的工程关了,未存改动丢失。
- 工具已护栏:`open_desktop`/`attach_desktop` 连上时记下已开的工程;`close_desktop`
  **只要实例里还开着不是本会话建/开的工程,就绝不退出 AEDT**,只关自己的工程。
  **自己写脚本时要守同一条**:连上先 `GetProjectList()`,非空就绝不 `QuitApplication`。
## 取远场前先确认 setup 的自适应频率落在谐振点上,否则 realized gain 是失配假象
- 现象:同一个天线,改了介质加载后重跑,`get_radiation_pattern` 的峰值增益从 +4.0 dBi 掉到 **−5.6 dBi**,
  方向图也不再是预期形状(峰值跑偏、单调下降)。看着像天线被改坏了。
- 原因:`get_radiation_pattern` 默认取 `LastAdaptive`,即 **setup 的自适应频率那一点**。
  几何/材料一改,谐振点跟着移动,原来设的自适应频率可能落到了谐振之外——
  **双频天线尤其危险,两个谐振之间就是失配峰**。realized gain 含失配损耗,自然塌掉。
- 判据:把 `get_s_parameters` 返回的各谐振 `-10dB` 区间和 setup 频率对一下,
  setup 频率不在任何一个区间内,远场就不能用。
- 解法:**为每个要考察的谐振点新建一个 setup**(频率设在该谐振上)再 analyze,用它的 LastAdaptive 取远场。
  顺手在该 setup 上挂一条 `Discrete + save_fields` 的扫频,一次求解同时拿到方向图和轴比曲线,省一轮。
- 引申:realized gain 天生含失配。要看天线本身的方向性,别在失配频点上比较增益。

## ⚠️ COM 复制 design(`CopyDesign`+`Paste`)会把多频自适应 setup 重置成单频 5 GHz
- 现象(2025.2 实测):原 design 的 3 个 setup 都是 MultiFrequency 27/38.5 GHz;`oProject.CopyDesign` + `Paste`
  出来的副本里,setup 名、扫频(含离散存场扫频)都在,但 `Solution Freq Type` 变成 Single、`Solution Freq = 5GHz`。
  在 24–40 GHz 天线上照样"收敛"(5 遍 ΔS 0.012),S11 却全乱:H 口低频段最差 −1.4 dB(真值 −10.9)。
  看着像"新加的结构把匹配搞坏了",差点去改接头。
- 查法:`oDesign.GetChildObject("Analysis").GetChildObject(s).GetPropValue("Solution Freq Type"/"Solution Freq")`。
- 修法:`EditSetup` 重写,多频表必须用 `NAME:` 嵌套写法(见 `_general.md` 同款坑):
  `"SolveType:=", "MultiFrequency", ["NAME:MultipleAdaptiveFreqsSetup", ["NAME:AdaptAt","Frequency:=","27GHz","Delta:=",0.02], ...]`。
  `SetPropValue("Solution Freq Type","Multiple")` 只会给出 2.5/5/10 GHz 默认表。EditSetup 不会删扫频。
- ⇒ **复制 design 后第一件事:核对每个 setup 的自适应频率**;收敛记录里网格单元数明显少于原 design 也是信号。

## 本征模 setup 不要发 `MeshLink` 块(老版本会直接拒绝)
- 现象:`InsertSetup("HfssEigen", ...)` 在 2019.2 上报 com_error,消息窗口写
  `The partner project name cannot be empty. Please finish the setup at the Setup Link dialog`。
  同一段参数在 2025.2 上完全正常。
- 原因:参数块里带了 `["NAME:MeshLink", "ImportMesh:=", False]`。2025.2 允许它存在且
  `ImportMesh:=False` 时无作用;**2019.2 只要这个块出现就要求给 partner project 名**。
- 解法:**不发这个块**。它只在跨工程链接网格时才需要,两个版本都正常。
- 通用教训:**从新版本录制出来的脚本,参数块可能比老版本能接受的更宽**。录制是摸参数结构
  最快的路,但录完要在老版本上回归一次 —— 多出来的块不一定被静默忽略,也可能直接报错。
